# gumanoid-sim — Unitree G1, Unitree H2 и Zeroth-01 в MuJoCo с ползунками (Docker, Ubuntu 24.04)

Docker-образ с физическим симулятором **MuJoCo 3.15** и тремя гуманоидами. Каждым суставом управляет
ползунок в окне MuJoCo: ползунок задаёт целевой угол, сервопривод тянет к нему сустав с настоящими
коэффициентами Kp и ограничением момента.

| Робот | Ползунков | Масса | Откуда модель |
|---|---|---|---|
| **Unitree G1** (29 суставов + кисти Dex3) | 43 | 34 кг | `unitreerobotics/xr_teleoperate` → `assets/g1/g1_body29_hand14.xml` |
| **Unitree H2** | 31 | 76 кг | `unitreerobotics/xr_teleoperate` → `assets/h2/H2.urdf` |
| **Zeroth-01** (K-Scale Z-Bot) | 16 | 2.6 кг | `Justin-Riekehof/zeroth-01-build` → `sim/assets/zbot-cad` |

Кроме того:

- для Zeroth-01 есть **ходьба** обученной нейросетью с управлением с клавиатуры и **демо** с записанными
  движениями (отжимания, взмах рукой и др.);
- **универсальный загрузчик** `robot` открывает с ползунками любого робота из файла URDF или MJCF: свои модели
  кладутся в папку `models/`, а в образ уже включены Unitree H1, H1-2, G1-23, R1 и кисти Dex3, Inspire, BrainCo;
- **примеры управления из кода**: Python-скрипт, который двигает робота при открытом окне, и сетевой мост
  (UDP + JSON), через который роботом управляет любая другая программа.

Внутри образа: Ubuntu 24.04, Python 3.12, MuJoCo 3.15.0, numpy 2.2.6, onnxruntime 1.23.2. Модели
скачиваются при сборке с GitHub на зафиксированных коммитах. Размер образа: ≈1.45 ГБ, сжатый в файл — ≈350 МБ.

## Быстрая установка

Одна команда в терминале Ubuntu (20.04, 22.04 или 24.04, с рабочим столом):

```bash
curl -fsSL https://raw.githubusercontent.com/garabot11/SIM/main/install.sh | bash
```

Если `curl` нет: `sudo apt install -y curl`. Или через git:

```bash
git clone https://github.com/garabot11/SIM.git ~/gumanoid && ~/gumanoid/install.sh
```

Скрипт `install.sh` сам делает всё, что описано в разделах 2–5:

1. скачивает проект в `~/gumanoid`;
2. ставит Docker, если его нет или он слишком старый, и добавляет вас в группу `docker`;
3. если есть видеокарта NVIDIA с драйвером — ставит NVIDIA Container Toolkit. **Без NVIDIA всё тоже работает:**
   рисует встроенная графика Intel/AMD, а если её нет — процессор;
4. собирает образ (первый раз 5–15 минут);
5. запускает самопроверку. Если с видеокартой она не проходит, а на процессоре проходит, запуск по умолчанию
   переключается на процессор;
6. создаёт команду `gumanoid` и ярлык **gumanoid-sim** в меню приложений.

Пароль `sudo` спросят только для установки пакетов. Запускать скрипт можно повторно: готовые шаги
пропускаются. После установки:

```bash
gumanoid               # меню с выбором робота (или ярлык gumanoid-sim в меню приложений)
gumanoid g1 --band     # сразу Unitree G1 на подвеске
gumanoid help          # все команды
```

`gumanoid` — то же самое, что `~/gumanoid/run.sh`: все команды и настройки из разделов 6–15 работают с обоими.
Если команда `gumanoid` не находится, выйдите из системы и войдите снова (тогда `~/.local/bin` попадёт в `PATH`)
или запускайте `~/.local/bin/gumanoid`.

Опции: `--no-nvidia` — не ставить NVIDIA Container Toolkit, `--no-test` — без самопроверки
(`curl … | bash -s -- --no-nvidia`). Другая папка: `curl … | GUMANOID_DIR=~/sim bash`.
Обновить проект: `cd ~/gumanoid && git pull && ./install.sh`.

Дальше можно сразу переходить к [разделу 6 «Запуск»](#6-запуск). Разделы 2–5 — что делает скрипт и как
сделать то же вручную.

## 1. Что нужно

- **Ubuntu 24.04** с рабочим столом. Окно симулятора открывается на экране этого компьютера. Работает и в
  сеансе Wayland (в Ubuntu 24.04 он по умолчанию, окно открывается через XWayland), и в сеансе Xorg.
  На **Ubuntu 22.04 и 20.04** тоже собирается и работает: внутри образа всегда Ubuntu 24.04, от системы
  компьютера нужен только Docker (особенности — в [пункте 2.4](#24-ubuntu-2204-и-2004)).
- Процессор x86_64, ≈4 ГБ свободного места на диске.
- Интернет на время сборки: скачиваются базовый образ Ubuntu, пакеты Python и модели с GitHub.
  Если интернета нет, можно перенести уже собранный образ файлом ([раздел 4, вариант Б](#вариант-б-готовый-образ-файлом-без-интернета)).
- Видеокарта любая:
  - **NVIDIA** — нужен драйвер и `nvidia-container-toolkit` ([раздел 3](#3-видеокарта-nvidia-по-желанию));
  - **Intel / AMD** — ничего ставить не надо;
  - **без видеокарты** — рисует процессор, работает медленнее, но работает.

## 2. Установка Docker на Ubuntu 24.04

Этот раздел `install.sh` выполняет сам ([быстрая установка](#быстрая-установка)); здесь — те же шаги вручную.
Если Docker уже стоит (`docker --version` что-то печатает), этот раздел можно пропустить, кроме пункта 2.3.

> Не ставьте Docker из **snap** (`snap install docker` или «Центр приложений»): у snap-версии свои ограничения
> доступа к файлам, экрану и видеокарте, и окно симулятора может не открыться. Если он уже стоит:
> `sudo snap remove docker`.

**2.1. Подключить официальный репозиторий Docker и поставить Docker Engine:**

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Если download.docker.com недоступен, поставьте Docker из репозитория Ubuntu: `sudo apt-get install -y docker.io docker-buildx`.

**2.2. Проверить, что Docker работает:**

```bash
sudo docker run --rm hello-world
```

Должно появиться `Hello from Docker!`. Если вместо этого ошибка про `registry-1.docker.io` (Docker Hub
недоступен), это не страшно для сборки: `build.sh` умеет скачать базовый образ сам ([раздел 5](#5-сборка-образа)).

**2.3. Разрешить своему пользователю запускать Docker без `sudo`:**

```bash
sudo usermod -aG docker $USER
```

После этого **выйдите из системы и войдите снова** (или перезагрузитесь). Проверка: `docker ps` без `sudo` не
должен ругаться на `permission denied`.

### 2.4. Ubuntu 22.04 и 20.04

Образ одинаковый на любой системе: всё, что внутри (Ubuntu 24.04, Python 3.12, MuJoCo), скачивается при сборке.
От компьютера нужны Docker, `bash` и `python3` (только для `docker/pull-image.py` и `examples/udp_client.py`;
оба работают с Python 3.8 и новее). Команды разделов 2–3 подходят без изменений: они сами подставляют
название версии Ubuntu (`jammy`, `focal`).

| | Ubuntu 22.04 | Ubuntu 20.04 |
|---|---|---|
| Docker из репозитория Docker (п. 2.1) | 29.x, как на 24.04 | 28.1.1: новее не будет, Docker перестал выпускать сборки для 20.04, но этой версии достаточно |
| Docker из репозитория Ubuntu (`docker.io docker-buildx`) | 29.1 | 26.1 (из `focal-updates`, нужен `sudo apt-get update`) |
| Python на компьютере | 3.10 | 3.8 |
| NVIDIA Container Toolkit (раздел 3) | да | да |
| Рабочий стол | Wayland (окно через XWayland) или Xorg | Xorg |

Проверьте версию Docker: `docker --version` должна быть **не ниже 20.10.10**. Более старый Docker (например,
19.03, который стоит в 20.04, если систему давно не обновляли) не умеет запускать внутри контейнера свежие
версии Ubuntu: сборка падает уже на первом `apt-get update` с ошибками вида `At least one invalid signature was
encountered`, `Couldn't create thread` или `Operation not permitted`. Лечится обновлением Docker по пункту 2.1
(или `sudo apt-get update && sudo apt-get install -y docker.io docker-buildx`).

Если `docker-buildx` не установлен, `docker build` пишет `DEPRECATED: The legacy builder is deprecated…` и
собирает старым сборщиком — образ получается тот же, предупреждение можно не замечать.

У Ubuntu 20.04 в мае 2025 закончилась обычная поддержка: обновления безопасности приходят только по подписке
Ubuntu Pro. Симулятор на ней работает, но систему по возможности стоит обновить.

## 3. Видеокарта NVIDIA (по желанию)

Нужно только для компьютеров с NVIDIA. С Intel/AMD или без видеокарты этот раздел пропустите.

**3.1. Драйвер.** Проверьте, что `nvidia-smi` показывает видеокарту. Если команды нет, поставьте драйвер:
`sudo ubuntu-drivers install`, затем перезагрузитесь.

**3.2. NVIDIA Container Toolkit** (через него контейнер получает доступ к видеокарте):

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

**3.3. Проверка** (после сборки образа): `./run.sh glinfo` должен показать в строке `OpenGL renderer` вашу
видеокарту NVIDIA. Или сразу: `docker run --rm --gpus all ubuntu:24.04 nvidia-smi`.

Если toolkit не ставить, симулятор всё равно запустится: `run.sh` сам переключится на встроенную графику
Intel/AMD или на программную отрисовку.

## 4. Как получить проект

Проект — это папка с этими файлами:

```
gumanoid/
├── README.md          эта инструкция
├── Dockerfile         рецепт образа (Ubuntu 24.04 + MuJoCo + модели)
├── .dockerignore      что не отправлять в сборку
├── .gitignore         что не хранить в git
├── install.sh         установка одной командой (Docker, сборка, команда gumanoid, ярлык)
├── build.sh           сборка образа
├── run.sh             запуск: окно симулятора на вашем экране
├── g1_sliders.py      Unitree G1 с ползунками
├── h2_sliders.py      Unitree H2 с ползунками
├── zbot_sliders.py    Zeroth-01 с ползунками
├── zbot_walk.py       Zeroth-01: ходьба с клавиатуры
├── zbot_demo.py       Zeroth-01: записанные движения
├── robot_sliders.py   любой робот (URDF/MJCF) с ползунками
├── examples/
│   ├── script_control.py   управление из Python-скрипта
│   ├── udp_bridge.py       управление по сети (сервер, в контейнере)
│   └── udp_client.py       пример клиента (на хосте, нужен только python3)
├── docker/
│   ├── sim            команда внутри контейнера (меню и подкоманды)
│   ├── selftest.py    самопроверка
│   └── pull-image.py  скачать базовый образ, если Docker Hub недоступен
├── models/            ваши роботы (создаётся при первом запуске; в контейнере — /models)
└── out/               скриншоты, сохранённые файлы, ваши скрипты (создаётся сам; в контейнере — /work)
```

### Вариант А: из GitHub или папкой с файлами (нужен интернет для сборки)

Проще всего скачать проект из репозитория (нужен `git`: `sudo apt install -y git`):

```bash
git clone https://github.com/garabot11/SIM.git ~/gumanoid
cd ~/gumanoid
```

Без доступа к GitHub проект можно перенести архивом. На компьютере, где проект уже есть, упакуйте его:

```bash
cd ~/gumanoid
tar czf ~/gumanoid-sim-src.tar.gz README.md Dockerfile .dockerignore install.sh build.sh run.sh \
    g1_sliders.py h2_sliders.py zbot_sliders.py zbot_walk.py zbot_demo.py robot_sliders.py \
    examples/*.py docker/sim docker/selftest.py docker/pull-image.py
```

Перенесите архив на другой компьютер (флешка, scp, мессенджер) и распакуйте:

```bash
mkdir -p ~/gumanoid && tar xzf gumanoid-sim-src.tar.gz -C ~/gumanoid
cd ~/gumanoid
```

Дальше — `./install.sh` (сделает всё сам) или вручную [сборка](#5-сборка-образа).

### Вариант Б: готовый образ файлом (без интернета)

На компьютере, где образ уже собран:

```bash
docker save gumanoid-sim | gzip > gumanoid-sim-image.tar.gz      # ≈350 МБ
```

На другом компьютере (Docker уже установлен, [раздел 2](#2-установка-docker-на-ubuntu-2404)):

```bash
docker load -i gumanoid-sim-image.tar.gz                         # появится образ gumanoid-sim
```

Для запуска понадобятся ещё `run.sh` и, по желанию, `examples/udp_client.py`: возьмите их из архива варианта А.
Собирать ничего не нужно, сразу переходите к [запуску](#6-запуск).

### Вариант В: через реестр образов (Docker Hub, GitHub Container Registry)

Если образ выложен в реестр (`docker tag gumanoid-sim <логин>/gumanoid-sim:1.0 && docker push <логин>/gumanoid-sim:1.0`),
на другом компьютере его можно скачать так:

```bash
docker pull <логин>/gumanoid-sim:1.0
IMAGE=<логин>/gumanoid-sim:1.0 ./run.sh
```

## 5. Сборка образа

`install.sh` собирает образ сам. Вручную (и после изменения скриптов):

```bash
cd ~/gumanoid
./build.sh
```

Что происходит при сборке (5–15 минут, большую часть времени занимает скачивание):

1. берётся базовый образ `ubuntu:24.04`. Если его ещё нет и `docker pull` не может его скачать (Docker Hub
   недоступен демону Docker), `build.sh` скачивает его скриптом `docker/pull-image.py` напрямую с Docker Hub
   через прокси терминала (`HTTPS_PROXY`) и загружает в Docker;
2. ставятся Python 3.12, git и библиотеки OpenGL/EGL/X11 (Mesa для Intel/AMD и программной отрисовки);
3. в отдельное виртуальное окружение `/opt/venv` ставятся `mujoco==3.15.0`, `glfw`, `numpy`, `onnxruntime`
   (в Ubuntu 24.04 системный pip закрыт, поэтому venv; он первый в `PATH`, и `python3` в контейнере — это он);
4. с GitHub скачиваются только нужные папки моделей на зафиксированных коммитах:
   - `Justin-Riekehof/zeroth-01-build @ 4b47eef` — модели Zeroth-01, политики ходьбы (ONNX), демо, позы сервоприводов;
   - `unitreerobotics/xr_teleoperate @ 845b25a` — папка `assets`: G1, H2, H1, H1-2, R1 и кисти;
5. копируются скрипты из папки проекта.

В конце `build.sh` печатает `Готово: образ gumanoid-sim, …`.

`build.sh` — это `docker build -t gumanoid-sim --network host .`, к которому добавлены прокси из
переменных `HTTP_PROXY`/`HTTPS_PROXY`, если они заданы. Без скрипта можно собрать так: `docker build -t gumanoid-sim .`.
Любые опции передаются дальше, например `./build.sh --no-cache` пересоберёт всё с нуля.

**Проверка образа без окна** (физика всех моделей, универсальный загрузчик, примеры, по одному кадру каждого робота):

```bash
./run.sh test
```

```
  [OK ] h2 кадр                      кадр selftest/h2.png
  [OK ] zbot кадр                    кадр selftest/zbot.png

Итог: 27/27 OK за 8 с
```

Кадры появятся в папке `out/selftest/` рядом с `run.sh`: там можно убедиться, что модели загрузились с текстурами.
В режимах `band` и `free` у G1 и H2 «ошибка слежения» большая — так и должно быть: робот стоит на полу или падает,
и суставы под нагрузкой не доходят до цели. Проверяется только, что физика не «взорвалась».

### Выбор видеокарты и другие настройки run.sh

`run.sh` сам определяет, чем рисовать, и пишет это первой строкой:
`run.sh: образ gumanoid-sim, графика: nvidia (PRIME offload), файлы: /home/<вы>/gumanoid/out, модели: /home/<вы>/gumanoid/models`.

Настройки задаются переменными перед командой:

| Переменная | Значения | По умолчанию |
|---|---|---|
| `GPU` | `nvidia` — видеокарта NVIDIA; `dri` — Intel/AMD через Mesa; `cpu` — программная отрисовка (llvmpipe) | `auto`: NVIDIA, если есть драйвер и toolkit, иначе Intel/AMD, иначе CPU |
| `PRIME` | `1` / `0` — рисовать на NVIDIA в ноутбуке с двумя видеокартами (экран подключён к встроенной) | `auto`: включается, если `xrandr --listproviders` показывает `NVIDIA-G0` |
| `IMAGE` | имя образа | `gumanoid-sim` |
| `OUT_DIR` | папка хоста для скриншотов, сохранённых файлов и своих скриптов (в контейнере `/work`) | `out` рядом с `run.sh` |
| `MODELS_DIR` | папка хоста со своими роботами (в контейнере `/models`, только чтение) | `models` рядом с `run.sh` |
| `NET` | `host` — контейнер в сети хоста: порты симулятора (например, UDP 9870) доступны как `127.0.0.1` | своя сеть контейнера |
| `DOCKER_ARGS` | любые дополнительные опции `docker run` | — |

Примеры: `GPU=cpu ./run.sh g1`, `GPU=dri ./run.sh h2 --band`, `OUT_DIR=~/Pictures ./run.sh zbot`,
`MODELS_DIR=~/robots ./run.sh robot go2/scene.xml`, `DOCKER_ARGS="-v $HOME/data:/data:ro" ./run.sh bash`.

Что `run.sh` передаёт в `docker run`:

- `-e DISPLAY -v /tmp/.X11-unix:/tmp/.X11-unix` и ваш файл `XAUTHORITY` — доступ к экрану; дополнительно
  `xhost +SI:localuser:$USER` разрешает X-серверу окна от вашего же пользователя (до перезахода в систему);
- `--user $(id -u):$(id -g)` — контейнер работает под вашим пользователем, и файлы в `out/` принадлежат вам, а не root;
- `-v ./out:/work` — рабочая папка контейнера; `-v ./models:/models:ro` — ваши модели;
- `--gpus all -e NVIDIA_DRIVER_CAPABILITIES=all` для NVIDIA, `--device /dev/dri` с группами `video`/`render` для Intel/AMD,
  `-e LIBGL_ALWAYS_SOFTWARE=1` для CPU;
- `--rm` — контейнер удаляется после выхода, ничего не копится; `--init` — чтобы Ctrl+C и `docker stop` закрывали симулятор сразу.

Ручной запуск без `run.sh` (Intel/AMD):

```bash
xhost +SI:localuser:$USER
mkdir -p out models
docker run --rm -it --init -e DISPLAY -v /tmp/.X11-unix:/tmp/.X11-unix:ro --device /dev/dri \
    $(for g in $(stat -c %g /dev/dri/card* /dev/dri/renderD* | sort -u); do echo --group-add $g; done) \
    --user $(id -u):$(id -g) -e HOME=/tmp -v "$PWD/out:/work" -v "$PWD/models:/models:ro" gumanoid-sim g1
```

Для NVIDIA добавьте `--gpus all`, для ноутбука с двумя видеокартами ещё
`-e __NV_PRIME_RENDER_OFFLOAD=1 -e __GLX_VENDOR_LIBRARY_NAME=nvidia`.

## 7. Окно MuJoCo: где ползунки и что за панели

G1, H2, Zeroth-01 и любые роботы через `robot` (команды `g1`, `h2`, `zbot`, `robot`, `demo`) открываются в
стандартном окне MuJoCo (*simulate*). Заголовок окна: `MuJoCo : G1 (on gumanoid-sim)`.

```
┌──────────────────────────── MuJoCo : G1 (on gumanoid-sim) ────────────────────────────┐
│ ▼ File           │                                              │ ◁ Joint    — углы     │
│ ▼ Option         │                                              │ ◁ Control  — ПОЛЗУНКИ │
│ ▼ Simulation     │                3D-сцена с роботом            │ ◁ Equality — подвеска │
│   Watch          │                                              │                       │
│   Physics        │                                              │                       │
│   Rendering      │                                              │                       │
│   Visualization  │                                              │                       │
│   Group enable   │                                              │                       │
└───────────────────────────────────────────────────────────────────────────────────────┘
  левая панель (Tab — скрыть/показать)                 правая панель (Shift+Tab — скрыть/показать)
```

### Как двигать суставы ползунками

1. **Разверните окно** на весь экран: двойной щелчок по заголовку или кнопка «□». В маленьком окне сцена узкая
   и робот виден не целиком. Можно ещё скрыть левую панель клавишей **Tab**.
2. В правой панели щёлкните по заголовку **Control** (или нажмите **Alt+C**). Раскроется список ползунков,
   по одному на сустав. Названия — как в таблицах ниже ([G1](#10-unitree-g1-суставы), [H2](#11-unitree-h2-суставы), [Zeroth-01](#12-zeroth-01-ползунки-ходьба-демо));
   для других роботов таблицу печатает терминал при запуске.
3. **Тяните ползунок мышью.** Значение — целевой угол в **радианах** (1 рад ≈ 57.3°); у поступательных
   суставов (slide) — смещение в метрах. Пределы ползунка равны пределам сустава. Сустав догоняет цель за доли
   секунды; если момента мотора не хватает (например, кисть или лодыжка под нагрузкой), он остановится раньше.
4. Кнопка **Clear all** (первая в разделе Control) ставит все цели в 0, то есть возвращает нулевую позу.
   Если 0 выходит за пределы сустава, ползунок упрётся в ближайший предел.
5. **Backspace** — полный сброс: поза, скорости, цели и подвеска возвращаются к началу (ключевая поза `home`).

Если правая панель слишком длинная (у G1 43 ползунка), прокручивайте её колесом мыши, наведя курсор на панель.
Ненужные разделы сворачиваются щелчком по заголовку. Шрифт панелей меняется в **Option → Font** (50–300 %).

### Правая панель

| Раздел | Клавиша | Что в нём |
|---|---|---|
| **Joint** | Alt+J | Текущие углы всех суставов (рад), то есть что получилось на самом деле. Ползунки здесь активны только **на паузе** (пробел): так можно поставить сустав в нужный угол напрямую, в обход привода. После снятия паузы привод потянет сустав обратно к цели из Control. |
| **Control** | Alt+C | **Ползунки управления**, по одному на привод, и кнопка **Clear all**. |
| **Equality** | Alt+E | Галочки связей. В режиме `--band` здесь одна галочка `band` — это подвеска таза. Снимите её, и робот останется на своих ногах; поставьте обратно, и подвеска вернёт таз на место (рывком, если робот успел упасть). В остальных режимах раздел пустой (или в нём связи самой модели, например пальцы схвата Panda). |

### Левая панель

| Раздел | Клавиша | Что в нём |
|---|---|---|
| **File** | Alt+F | `Save xml` (для этих моделей не работает, см. [раздел 16](#16-файлы-скриншоты-сохранение-сцены)), `Save mjb` — бинарная модель, `Print model` / `Print data` — текстовый дамп модели или состояния, `Quit` (Ctrl+Q) — выход, `Screenshot` (Ctrl+P) — снимок экрана. |
| **Option** | Alt+O | `Help` (F1) — подсказка по клавишам прямо в окне, `Info` (F2) — время и решатель, `Profiler` (F3) — графики производительности, `Sensor` (F4) — графики датчиков, `Fullscreen` (F5), `Vertical Sync`, `Busy Wait`, `Spacing`, `Color` и `Font` — вид панелей. |
| **Simulation** | Alt+S | `Pause` / `Run` — пауза и пуск; `Num threads` — потоки физики (оставьте 0); `Reset` (Backspace) — сброс; `Reload` (Ctrl+L) — перечитать модель из файла (здесь не используется); `Align` (Ctrl+A) — вернуть камеру в исходный вид; `Copy state` (Ctrl+C) — скопировать текущую позу в буфер обмена как `<key>` в формате MJCF; `Key` + `Load key` — загрузить сохранённую позу (0 = исходная `home`); `Save key` — запомнить текущую позу в выбранный `Key` (только до закрытия окна); `Noise scale` / `Noise rate` — случайный шум на всех ползунках («дрожание», проверка устойчивости); `History` — перемотка назад по последним кадрам. |
| **Watch** | Alt+W | Показать любое поле состояния: в `Field` введите, например, `qpos`, в `Index` — номер, в `Value` появится значение. |
| **Physics** | Alt+P | Параметры физики: интегратор, решатель, шаг (`Timestep`), гравитация, ветер и т.д. В `Disable Flags` можно, например, выключить гравитацию (`Gravity`) или контакты (`Contact`). `Actuator Group Enable` включает и выключает группы приводов (у нас все в группе 0). |
| **Rendering** | Alt+R | `Camera` — `Free` (свободная) или `Tracking` (следит за выбранным телом). `Label` — подписи (имена тел, суставов…), `Frame` — оси координат. `Model Elements` — что рисовать (горячие клавиши в таблице ниже). `OpenGL Effects` — тени, отражения, каркас. |
| **Visualization** | Alt+V | Свет, поле зрения камеры, масштаб стрелок сил и контактов, цвета служебных элементов. |
| **Group enable** | Alt+G | Видимость групп геометрии (клавиши 0–5), сайтов (Shift+0–5), суставов, приводов. У G1, H2 и роботов через `robot` **группа 3** — упрощённая геометрия столкновений, по умолчанию скрыта: нажмите **3**, чтобы её увидеть. |

## 8. Клавиши и мышь

Чтобы клавиши работали, окно должно быть активным: щёлкните по 3D-сцене. Буквенные клавиши срабатывают
по физическому положению, как на английской раскладке, переключать раскладку не нужно.

### Мышь (в 3D-сцене)

| Действие | Что делает |
|---|---|
| Левая кнопка + тянуть | вращать камеру вокруг центра |
| Правая кнопка + тянуть | сдвигать камеру (с Shift — в горизонтальной плоскости) |
| Колесо или средняя кнопка + тянуть | приблизить или отдалить |
| Двойной щелчок левой по детали | выбрать тело (подсветится) |
| Двойной щелчок правой по точке | сделать эту точку центром вращения камеры |
| Ctrl + двойной щелчок правой | камера следит за выбранным телом |
| **Ctrl + левая + тянуть** | **повернуть выбранное тело** (приложить к нему момент, «толкнуть рукой») |
| **Ctrl + правая + тянуть** | **потянуть выбранное тело** (приложить силу); с Shift — в другой плоскости |
| Удерживать правую кнопку над панелью | показать горячие клавиши элементов панели |
| Двойной щелчок по заголовку раздела | развернуть или свернуть все разделы |

Пример: двойным щелчком выберите кисть G1, затем с зажатым Ctrl тяните её правой кнопкой — рука пойдёт за мышью,
сопротивляясь приводами.

| Клавиша | Действие |

## 9. Режимы: подвес, подвеска, свободно

| Режим | Команда | Что происходит |
|---|---|---|
| **Подвес** (по умолчанию) | `g1`, `h2`, `zbot`, `robot …` | Таз (корень робота) жёстко закреплён в воздухе, ноги не достают до пола. Удобно двигать любые суставы, робот не упадёт. У G1, H2 и в `robot` включена **компенсация силы тяжести**: приводы держат вес звеньев, как это делает контроллер настоящего робота, и сустав встаёт ровно в угол с ползунка (ошибка < 1°). Манипуляторы (модели без свободной базы) остаются стоять там, где их поставил автор модели. |
| **Подвеска** | `g1 --band`, `h2 --band`, `robot … --band` | Робот стоит на полу, а таз держит жёсткая упругая связь, как страховочный трос на стенде. Стопы несут часть веса (G1 — около 2/3, H2 — около половины), остальное держит подвеска. Можно двигать ногами по полу; при приседании таз остаётся на месте, а стопы отрываются от пола. В правой панели **Equality → band** снимите галочку, и робот останется без опоры. Backspace возвращает подвеску. Компенсации силы тяжести нет: под весом торса поясница G1 наклоняется примерно на 20°. |
| **Свободно** | `g1 --free`, `h2 --free`, `zbot --free`, `robot … --free` | Робот стоит на полу без опоры. Контроллера баланса нет, поэтому G1 и H2 **падают** за пару секунд: одних Kp суставов не хватает, чтобы удержать равновесие. Zeroth-01 лёгкий и в нулевой позе стоит. |

Как работает привод: `момент = Kp·(цель − угол) − Kd·скорость`, обрезается по максимальному моменту мотора.
У G1, H2 и Zeroth-01 Kp — штатные коэффициенты производителя. Kd по умолчанию рассчитан на критическое
демпфирование (без раскачки), `--unitree-kd` берёт Kd как в Unitree SDK. Как подбираются коэффициенты для
других роботов — в [разделе 14.4](#144-как-выбрать-kp-kd-и-предельный-момент).

### Ходьба с клавиатуры (`./run.sh walk`)

Робот идёт обученной нейросетью (политикой) из репозитория. Окно своё, не стандартное окно MuJoCo:

| Клавиша | Действие |
|---|---|
| ← / → или A / D (держать) | поворот |
| ↑ / ↓ или W / S (держать) | быстрее / медленнее |
| Пробел | пауза |
| R или Backspace | начать заново |
| 1 … 5 | сменить политику на ходу (1 — самая медленная, 5 — самая быстрая) |
| Tab или C | камера следует за роботом / свободная |
| H | показать или скрыть подсказку |
| Esc | выход |
| Мышь | левая — вращать камеру, правая — сдвигать, колесо — приближать (Shift меняет плоскость) |

Остановиться на месте и идти назад политики не умеют: их обучали только идти вперёд. Поэтому «стоп» —
это пауза. Если робот упал, через секунду он начнёт заново. Конкретную политику и параметры можно задать:
`./run.sh walk --policy cad2_v10_calm2_step850 --speed 0.15 --freq 1.6`, список — `./run.sh walk --list`.

### Записанные движения (`./run.sh demo <имя>`)

Это последовательности поз, которые на настоящем роботе проигрывает его прошивка; здесь — с физикой.

| Демо | Результат в симуляторе |
|---|---|
| `push_ups` | работает: робот ложится вперёд на руки и делает 5 отжиманий |
| `wave` | работает: машет рукой |
| `kneeing` | с рюкзаком падает назад; с `--no-backpack` проходит целиком |
| `walk_0`, `careful_walk` | падает: шаги без контроллера баланса |

Опции: `--no-backpack` — без рюкзака; `--until N` — только первые N шагов; `--start zero` — старт из нулевой
позы вместо стойки; `--headless` — без окна, итог по шагам в консоль. Ход демо печатается в терминал, а в
окне вверху слева видно имя демо и время. После последнего шага робот держит позу, пока окно открыто.

## 13. Другие роботы: как подключить своего

Любой робот, описанный в формате **URDF** (принят в ROS) или **MJCF** (родной формат MuJoCo, файлы `.xml`),
открывается с ползунками одной командой:

```bash
./run.sh robot <файл или короткое имя> [опции]
```

Это скрипт `robot_sliders.py` — универсальный загрузчик. Он сам добавляет пол и свет, ставит сервопривод на
каждый сустав, подбирает коэффициенты и печатает в терминал таблицу ползунков.

### 13.1. Встроенные модели Unitree

В образ уже входят все модели из `xr_teleoperate/assets`. Те, у которых нет своего скрипта, открываются через `robot`
по короткому имени:

| Имя | Робот | Ползунков | Масса | Файл в `xr_teleoperate/assets` |
|---|---|---|---|---|
| `h1` | Unitree H1 с кистями Inspire | 33 | 52 кг | `h1/h1_with_hand.urdf` |
| `h1_2` | Unitree H1-2 с кистями Inspire | 39 | 67 кг | `h1_2/h1_2.urdf` |
| `g1_23` | Unitree G1, 23 сустава (без кистей) | 23 | 34 кг | `g1/g1_body23.urdf` |
| `r1` | Unitree R1 (A7) | 17 | 17 кг | `r1/r1_a7.urdf` |
| `r1_a5` | Unitree R1 (A5) | 13 | 14 кг | `r1/r1_a5.urdf` |
| `dex3` | кисть Unitree Dex3, левая | 7 | 0.7 кг | `unitree_hand/unitree_dex3_left.urdf` |
| `inspire` | кисть Inspire, левая | 6 | 0.2 кг | `inspire_hand/inspire_hand_left.urdf` |

Примеры: `./run.sh robot h1`, `./run.sh robot h1_2 --band`, `./run.sh robot dex3`. Имена `g1` и `h2` тоже

чтобы сравнить. Вторые варианты кистей
(правые) открываются полным путём, например
`./run.sh robot /opt/gumanoid/xr_teleoperate/assets/inspire_hand/inspire_hand_right.urdf`.
Посмотреть, что доступно: `./run.sh models`.

Коэффициенты у этих моделей подобраны автоматически (см. [14.4](#144-как-выбрать-kp-kd-и-предельный-момент)), а не
взяты из SDK, как у G1 и H2. В подвесе разницы не видно; на полу шагающие роботы без контроллера баланса падают.

### 13.2. Свой робот за три шага

**Шаг 1. Найти модель.** Где взять:

- **MuJoCo Menagerie** — [github.com/google-deepmind/mujoco_menagerie](https://github.com/google-deepmind/mujoco_menagerie):
  десятки готовых и выверенных моделей в MJCF (Unitree Go1/Go2/H1/G1/Z1, Boston Dynamics Spot, Franka Panda,
  UR5e/UR10e, Kinova, Robotis OP3, кисти Shadow/Allegro/LEAP и др.). Берите файл `scene.xml` (в нём робот
  уже стоит на полу со светом) или `<робот>.xml`.
- **URDF из ROS-пакета производителя** — обычно репозиторий `<робот>_description`: папка `urdf/` с файлом
  `.urdf` (или `.xacro`, его нужно сначала превратить в URDF: `xacro robot.urdf.xacro > robot.urdf` в ROS) и
  папка `meshes/`.
- **Экспорт из CAD**: [onshape-to-robot](https://github.com/Rhoban/onshape-to-robot) (Onshape → URDF или MJCF),
  SolidWorks to URDF Exporter, плагины для Fusion 360 и Blender (Phobos).

**Шаг 2. Положить в папку `models/`** рядом с `run.sh` (она создаётся при первом запуске; в контейнере это
`/models`). Кладите **всю папку модели** вместе с мешами: URDF и MJCF ссылаются на файлы `.stl`/`.obj` по
относительным путям. Если в URDF пути вида `package://имя_пакета/meshes/...`, положите ROS-пакет целиком
(папку `имя_пакета/` с `urdf/` и `meshes/` внутри): загрузчик найдёт меши сам.

Пример — квадропед Unitree Go2 и манипулятор Franka Panda из Menagerie:

```bash
cd ~/gumanoid/models
git clone --depth 1 --filter=blob:none --sparse https://github.com/google-deepmind/mujoco_menagerie.git
cd mujoco_menagerie && git sparse-checkout set unitree_go2 franka_emika_panda && cd ../..
```

Получится `models/mujoco_menagerie/unitree_go2/scene.xml` и `models/mujoco_menagerie/franka_emika_panda/scene.xml`.

**Шаг 3. Запустить.** Путь указывается относительно `models/`:

```bash
./run.sh robot mujoco_menagerie/unitree_go2/scene.xml --free
./run.sh robot mujoco_menagerie/franka_emika_panda/scene.xml
```

или через меню: пункт 12 → номер модели → режим. В терминале появится таблица ползунков:

```

    1 FL_hip                         -60.0° ..   60.0°     25.57    1.853       23.70
    2 FL_thigh                       -90.0° ..  200.0°     19.20    1.528       23.70
    3 FL_calf                       -156.0° ..  -48.0°     10.31    0.821       45.43
    4 FR_hip                         -60.0° ..   60.0°     25.57    1.853       23.70

```

Проверено с этим загрузчиком (подвес и пол, 1.5 с физики без ошибок): G1, H2, Zeroth-01 (`.mjcf`), все модели
Unitree из `xr_teleoperate` (URDF и MJCF), а из Menagerie — Unitree Go2, Unitree H1, Franka Panda, Robotis OP3.

### 13.3. Что делает загрузчик

1. **Читает модель.** URDF: находит меши (`package://…`, относительные пути, а если не нашёл — ищет файл с тем
   же именем рядом), включает в MuJoCo-импорте визуальные меши и отключает слияние неподвижных звеньев.
   MJCF: читает как есть, вместе с `<include>`; файлы `.mjcf` читаются как текст (тогда `<include>` не работают).
2. **Сцена.** Если в модели нет пола, добавляет пол в клетку, небо и два источника света. Если пол есть
   (например, `scene.xml` из Menagerie), оставляет сцену модели.
3. **Исходная поза.** Если в модели есть ключевая поза `home` (или указана `--key`), робот стартует в ней,
   иначе все суставы в нуле.
4. **База.** Корень робота — тело верхнего уровня с наибольшим числом суставов под ним.
   Подвес: свободная база (`freejoint`) удаляется, робот поднимается так, чтобы нижняя точка была на 10 см
   над полом. Модель без свободной базы (манипулятор) остаётся на месте; если она «утоплена» в пол — поднимается.
   `--free`/`--band`: если свободной базы нет (в URDF её не бывает), она добавляется, и робот ставится на пол.
5. **Столкновения.** Звенья робота сталкиваются с полом и предметами, но не друг с другом (меши соседних звеньев
   часто перекрываются уже в нулевой позе и иначе «расталкивают» робота). `--self-collision` — оставить как в модели.
   Если у звена есть отдельные визуальные меши, геометрия столкновений прячется в группу 3 (клавиша **3** — показать).
6. **Приводы = ползунки.** На каждый сустав `hinge` (вращательный) или `slide` (поступательный) ставится
   позиционный сервопривод: ползунок = цель, пределы = пределы сустава (если их нет — ±180° или ±1 м).
   Суставы, которые модель сама ведёт через `<equality joint>` или `mimic` в URDF (один из двух пальцев схвата,
   фаланги пальцев кистей Inspire у H1), пропускаются.
   Старые моторы модели (`<motor>`: ctrl = момент) удаляются, но их предельный момент запоминается.
   Если **все** приводы модели уже позиционные (как у манипуляторов в Menagerie), они остаются как есть,
   вместе с приводами схвата на сухожилиях (`--actuators replace` — заменить всё равно).
7. **Коэффициенты** подбираются под массу и размеры робота ([14.4](#144-как-выбрать-kp-kd-и-предельный-момент)).
8. **Компенсация силы тяжести** в подвесе, как у G1/H2.
9. Ключевая поза `home` (Backspace), стартовая камера на весь робот — и открывается окно.

### 13.4. Опции `robot`

| Опция | Что делает |
|---|---|
| (нет) | подвес: корень закреплён, компенсация силы тяжести |
| `--free` | на полу без опоры |
| `--band` | на полу на подвеске (галочка `band` в Equality) |
| `--no-gravcomp` | без компенсации силы тяжести в подвесе |
| `--kp K` | жёсткость всех приводов, Н·м/рад (по умолчанию — подбор) |
| `--kv C` | демпфирование всех приводов, Н·м·с/рад (по умолчанию — критическое) |
| `--freq F` | собственная частота привода при подборе kp, Гц (по умолчанию 4; меньше — мягче) |
| `--effort N` | предельный момент всех приводов, Н·м (по умолчанию — из модели: `effort` в URDF, `actuatorfrcrange`, `ctrlrange` моторов) |
| `--gains файл.json` | свои kp/kv/effort/armature для отдельных суставов, см. ниже |
| `--key ИМЯ` | стартовая поза: имя или номер `<key>` модели; `none` — нули |
| `--exclude РЕГВЫР` | суставы без ползунков, например `--exclude 'finger|hand'` |
| `--actuators keep\|replace` | оставить приводы модели / заменить своими (по умолчанию — автоматически) |
| `--self-collision` | не выключать столкновения звеньев друг с другом |
| `--info` | только напечатать таблицу ползунков и выйти |
| `--save-xml ФАЙЛ` | сохранить собранную сцену в MJCF (в `out/`) и выйти |

**Файл коэффициентов** (`--gains`): ключ — регулярное выражение по имени сустава, значение — любые из `kp`,
`kv`, `effort`, `armature`. Первое подошедшее выражение побеждает. Файл кладите в `out/` (это рабочая папка
контейнера) или рядом с моделью в `models/`. Пример для Go2 — `out/go2_gains.json`:

```json
{
  "_hip_joint|_thigh_joint": {"kp": 60, "kv": 2.0},
  "_calf_joint":             {"kp": 60, "kv": 2.0}
}
```

```bash
./run.sh robot mujoco_menagerie/unitree_go2/scene.xml --free --gains go2_gains.json
```

С подобранными коэффициентами (kp 10–26) Go2 на полу оседает под своим весом: корпус за 4 секунды опускается с
0.30 до 0.16 м. С этим файлом он стоит в позе `home` (корпус на 0.26 м). Подбор считает только вес звеньев за
суставом, а ногам на полу приходится держать весь корпус — поэтому шагающим роботам на полу коэффициенты лучше
задать самим (из SDK производителя или так, как здесь). Предельные моменты (23.7 и 45.4 Н·м) взяты из моторов модели.

### 13.5. Если модель не открывается

| Сообщение | Что делать |
|---|---|
| `не найдены меши` | положите папку `meshes/` (или ROS-пакет целиком) рядом с URDF; пути в URDF должны вести к файлам |
| `MuJoCo не читает … .dae` | MuJoCo читает меши только `.stl`, `.obj`, `.msh`. Переведите `.dae` в `.stl`/`.obj` (Blender: File → Import Collada → Export STL; или `assimp export a.dae a.obj`) и поправьте имена в URDF |
| `mass and inertia of moving bodies must be larger than mjMINVAL` | у подвижного звена в URDF нет `<inertial>` или масса 0. Впишите массу и инерцию; временно — `<mujoco><compiler inertiafromgeom="true"/></mujoco>` внутри `<robot>` |
| `repeated name` | два элемента с одинаковым именем (часто — два одинаковых меша). Переименуйте один в URDF/MJCF |
| `модель «…» не найдена` | путь указывается относительно `models/` (или полный путь внутри контейнера); `./run.sh models` покажет, что видно |
| робот дрожит или «взрывается» | уменьшите жёсткость: `--freq 2` или `--kp …`; проверьте массы звеньев (`--info` печатает массу) |
| сустав крутится не туда / не в том месте | ошибка оси или начала координат в URDF; включите оси суставов клавишей **J** и подписи **F7** |
| ползунков нет, а суставы есть | все суставы в `--exclude` или ведомые; посмотрите `--info` |

## 14. Как сделать ползунки для робота

### 14.1. Принцип

В окне MuJoCo ползунок в разделе **Control** появляется **для каждого привода** (`<actuator>`) модели:
значение ползунка — это `ctrl` привода, пределы ползунка — его `ctrlrange`. Своих ползунков окно делать не
умеет, поэтому «сделать ползунки» = «добавить в модель приводы». Что значит ctrl, зависит от типа привода:

| Привод (MJCF) | ctrl = | Когда нужен |
|---|---|---|
| `<position joint=… kp=… kv=…>` | целевой угол (рад) или положение (м) | **ползунки суставов** — как во всех скриптах проекта; так работают сервоприводы и моторы Unitree в режиме PD |
| `<velocity joint=… kv=…>` | целевая скорость | колёса, конвейеры |
| `<motor joint=… gear=…>` | момент (Н·м) или сила (Н) | прямое управление моментом (так модели описывают для обучения политик) |
| `<general …>` | что угодно (`gainprm`/`biasprm`) | нестандартные приводы, PD с особыми коэффициентами |
| `tendon=…` вместо `joint=…` | то же, но для сухожилия | один ползунок на несколько суставов (схват, пальцы) |
| `site=…` | сила/момент в точке | двигатели, реактивные силы |

Позиционный привод MuJoCo — это ровно PD-регулятор мотора: `момент = kp·(ctrl − q) − kv·q̇`, обрезанный по
`forcerange`.

### 14.2. Ползунки в XML (MJCF)

Пусть есть сустав `<joint name="left_knee_joint" range="-0.09 2.88"/>`. Ползунок для него:

```xml
<actuator>
  <position name="left_knee" joint="left_knee_joint" kp="100" kv="4"
            ctrlrange="-0.09 2.88" forcerange="-139 139"/>
</actuator>
```

`ctrlrange` ставьте равным `range` сустава, `forcerange` — предельному моменту мотора. Модель проверяется так:
файл кладётся в `out/`, затем `./run.sh viewer мой_робот.xml`.

**У URDF приводов нет** — в формате их просто не бывает. Самый короткий путь получить MJCF с ползунками из URDF:

```bash
./run.sh robot my_robot/robot.urdf --save-xml my_robot.xml    # в out/ появится MJCF с полом и приводами
nano out/my_robot.xml                                         # поправить kp, пределы, имена…
./run.sh viewer my_robot.xml                                  # открыть исправленное
```

Пути к мешам в сохранённом файле абсолютные и указывают внутрь контейнера (`/models/...`), поэтому
открывайте его через `./run.sh viewer`.

### 14.3. Ползунки из Python (MjSpec)

Так устроены все скрипты проекта: модель читается в `MjSpec` (редактируемое описание), к ней добавляются пол и
приводы, потом она компилируется в `MjModel`. Минимальный пример для своего скрипта (`out/my_sliders.py`):

```python
import mujoco, mujoco.viewer

spec = mujoco.MjSpec.from_file("/models/my_robot/robot.xml")   # MJCF; для URDF удобнее build_spec ниже — он сам найдёт меши
spec.worldbody.add_geom(type=mujoco.mjtGeom.mjGEOM_PLANE, size=[0, 0, 0.05])   # пол
spec.worldbody.add_light(pos=[0, 0, 3], dir=[0, 0, -1])

for j in spec.joints:
    if j.type != mujoco.mjtJoint.mjJNT_HINGE:
        continue
    act = spec.add_actuator(name=j.name, target=j.name, trntype=mujoco.mjtTrn.mjTRN_JOINT)
    act.set_to_position(kp=50, kv=2)          # PD-сервопривод
    act.ctrllimited = mujoco.mjtLimited.mjLIMITED_TRUE
    act.ctrlrange = j.range                   # ползунок от предела до предела сустава
    act.forcelimited = mujoco.mjtLimited.mjLIMITED_TRUE
    act.forcerange = [-30, 30]                # предельный момент, Н·м

model = spec.compile()
mujoco.viewer.launch(model, mujoco.MjData(model))
```

Запуск: `./run.sh python my_sliders.py`. Чтобы не повторять всё вручную, возьмите готовую сборку и поменяйте
только своё:

```python
from pathlib import Path
from robot_sliders import build_spec
spec = build_spec(Path("/models/my_robot/robot.urdf"), free=False, kp=80)
spec.actuator("left_knee").forcerange = [-60, 60]     # что-то поправить после сборки
```

Полезные мелочи MuJoCo 3.15, на которых легко споткнуться: `joint.damping` — вектор (`[d, 0, 0]`), матрица масс —
`mujoco.mj_fullM(model, data, dst)`, `MjSpec.from_file` не принимает расширение `.mjcf` (читайте текст через
`from_string` и задайте `spec.meshdir`), после сборки из `MjSpec` сохраняйте модель через `spec.to_xml()`
(кнопка **Save xml** в окне не работает), у `weld`-связи из `MjSpec` нужно явно задать `data=[0]*10+[1]`.

### 14.4. Как выбрать Kp, Kd и предельный момент

- **Есть данные производителя** — берите их: у G1 и H2 Kp из примеров Unitree SDK, у Zeroth-01 — из параметров
  сервоприводов Feetech. Это ближе всего к настоящему роботу.
- **Данных нет** — загрузчик подбирает так (то же можно делать вручную):
  - `kp = max(M·(2π·f)², G / 0.05 рад)`: `M` — инерция, которую «видит» сустав (диагональ матрицы масс), `f` —
    желаемая собственная частота (по умолчанию 4 Гц, `--freq`), `G` — наибольший момент силы тяжести на суставе
    (масса всего, что за ним, × g × плечо). Первое слагаемое даёт одинаково быстрый отклик на любом роботе, второе
    не даёт суставу провисать больше чем на ~3°;
  - `kv = 2·√(kp·M)` — критическое демпфирование: сустав приходит к цели без раскачки;
  - если `kp` получился большим для лёгкого звена (неустойчиво при шаге 2 мс), добавляется `armature` —
    приведённая инерция ротора мотора, которая у настоящих моторов есть всегда.
- **Предельный момент** (`forcerange`) — из паспорта мотора (`effort` в URDF). Без него сервопривод всемогущ, и
  робот поднимет что угодно.
- **Компенсация силы тяжести** (`body.gravcomp = 1` + `joint.actgravcomp = True`) — только для закреплённой базы:
  с ней сустав встаёт ровно в угол ползунка при любом Kp. На полу её включать нельзя — робот станет невесомым.

### 14.5. Свой робот как отдельная команда в образе

Чтобы робот открывался коротко (`./run.sh myrobot`) и был встроен в образ:

1. Положите модель в проект, например в `assets/myrobot/`, и добавьте в `Dockerfile` строку
   `COPY assets/ assets/` (а в `.dockerignore` — строку `!assets/**`).
2. Создайте `myrobot_sliders.py` по образцу `h2_sliders.py` (свои Kp/Kd по суставам, режимы) или совсем
   коротко — через универсальный загрузчик:
   ```python
   #!/usr/bin/env python3
   import sys
   from pathlib import Path
   import mujoco, mujoco.viewer
   from robot_sliders import build_spec
   spec = build_spec(Path("/opt/gumanoid/assets/myrobot/robot.urdf"), free="--free" in sys.argv,
                     gains=Path("/opt/gumanoid/assets/myrobot/gains.json"))
   model = spec.compile()
   data = mujoco.MjData(model)
   mujoco.mj_resetDataKeyframe(model, data, model.key("home").id)
   mujoco.viewer.launch(model, data)
   ```
3. Добавьте файл в `COPY … ./` в `Dockerfile` и в `.dockerignore` (`!myrobot_sliders.py`).
4. В `docker/sim` добавьте строку в `case`: `myrobot) py "$APP/myrobot_sliders.py" "$@" ;;` и, по желанию,
   пункт меню в массив `items` (формат `"Подпись|команда"`).
5. `./build.sh` (пересоберётся только слой со скриптами, секунды) и `./run.sh myrobot`.

Без пересборки можно проще: положить `myrobot_sliders.py` в `out/` и запускать `./run.sh python myrobot_sliders.py`.

### 14.6. Другие способы двигать робота в окне

- **Мышью**: двойной щелчок по звену, затем Ctrl + правая кнопка — тянуть, Ctrl + левая — поворачивать ([раздел 8](#8-клавиши-и-мышь)).
- **Раздел Joint на паузе**: ползунки прямо по суставам, в обход приводов — удобно выставить позу.
- **Ключевые позы**: Ctrl+C копирует текущую позу как `<key qpos=… ctrl=…/>`; вставьте её в MJCF-файл в
  `<keyframe>`, и поза будет доступна через Simulation → Key → Load key.
- **Mocap-тела** (`<body mocap="true">`) двигаются мышью (Ctrl + правая) и могут тянуть робота через `weld`-связь —
  так делают телеуправление «рукой за кисть».

### 15.1. Python-скрипт: пример `script_control`

обычно, а ползунки Control перезаписываются скриптом.

Чтобы сделать своё: скопируйте пример в `out/` и правьте функцию `control()`:

```bash
docker run --rm gumanoid-sim cat /opt/gumanoid/examples/script_control.py > out/my_control.py
./run.sh python my_control.py h2
```

Минимальный каркас своего скрипта:

```python
import time
import mujoco, mujoco.viewer
import numpy as np
from robot_sliders import load_robot           # g1, h2, zbot, h1 … или путь к модели

model = load_robot("h2").compile()             # free=True / band=True — на полу
data = mujoco.MjData(model)
mujoco.mj_resetDataKeyframe(model, data, model.key("home").id)
elbow = model.actuator("left_elbow").id

with mujoco.viewer.launch_passive(model, data) as viewer:     # окно, физику крутит скрипт
    while viewer.is_running():
        t0 = time.time()
        with viewer.lock():                                   # окно читает data из своего потока
            for _ in range(8):                                # 8 шагов по 2 мс = один кадр (~60 к/с)
                data.ctrl[elbow] = 0.8 * np.sin(data.time)    # цель привода, рад
                mujoco.mj_step(model, data)                   # шаг физики
        viewer.sync()                                         # показать кадр
        time.sleep(max(0, 8 * model.opt.timestep - (time.time() - t0)))   # реальное время
```

`viewer.sync()` — дорогая операция, поэтому окно обновляется раз в несколько шагов физики, а не на каждом:
иначе симуляция идёт медленнее реального времени.

Шпаргалка по тому, что читать и писать (`m` = `model`, `d` = `data`):

| Что | Как |
|---|---|
| задать цель привода (ползунок) | `d.ctrl[i] = …` или `d.actuator("left_elbow").ctrl = …` |
| номер привода / сустава / тела по имени | `m.actuator("left_elbow").id`, `m.joint("left_knee_joint").id`, `m.body("pelvis").id` |
| угол и скорость сустава | `d.joint("left_knee_joint").qpos`, `.qvel` (все сразу — `d.qpos`, `d.qvel`) |
| что сделал привод | `d.actuator_length[i]` (угол), `d.actuator_velocity[i]`, `d.actuator_force[i]` (момент) |
| положение и ориентация тела | `d.body("pelvis").xpos` (м), `.xquat` (w, x, y, z), `.xmat` |
| центр масс робота | `d.subtree_com[1]` |
| контакты и силы | `d.ncon`, `d.contact[k].geom1/geom2/pos`, сила — `mujoco.mj_contactForce(m, d, k, f6)` |
| толкнуть тело | `d.xfrc_applied[body] = [Fx, Fy, Fz, Mx, My, Mz]` (держится, пока не обнулить) |
| датчики модели | `d.sensordata`, `d.sensor("имя").data` |
| шаг / пересчёт без шага | `mujoco.mj_step(m, d)` / `mujoco.mj_forward(m, d)` |
| сброс в позу `home` | `mujoco.mj_resetDataKeyframe(m, d, m.key("home").id)` |
| время, шаг | `d.time`, `m.opt.timestep` |
| гравитация, трение пола и т.п. | `m.opt.gravity`, `m.geom_friction[…]` — можно менять на ходу |

Документация API: [mujoco.readthedocs.io](https://mujoco.readthedocs.io/en/stable/python.html).

**Без окна и с картинкой** (обучение, сбор данных, видео): цикл с `mj_step` без viewer работает в десятки раз
быстрее реального времени, а кадры рисует `mujoco.Renderer`:

```python
import os; os.environ.setdefault("MUJOCO_GL", "egl")    # до import mujoco; без видеокарты — "osmesa"
import sys
from pathlib import Path
import mujoco
sys.path.insert(0, "/opt/gumanoid/docker"); from selftest import write_png   # PNG без лишних библиотек
...
with mujoco.Renderer(model, 480, 640) as r:
    r.update_scene(data)          # можно передать камеру: r.update_scene(data, camera="имя")
    write_png(Path(f"frame_{n:05d}.png"), r.render())
```

Кадры попадут в `out/`; видео из них на хосте: `ffmpeg -framerate 30 -i out/frame_%05d.png out/video.mp4`.

**Дополнительные пакеты Python** ставятся в свой образ поверх этого (venv в образе принадлежит root):

```dockerfile
FROM gumanoid-sim
USER root
RUN pip install --no-cache-dir scipy matplotlib
```

`docker build -t gumanoid-sim-plus -f Dockerfile.plus .`, затем `IMAGE=gumanoid-sim-plus ./run.sh`.

### 15.2. Другая программа по сети: пример `udp_bridge`

Симулятор слушает UDP-порт 9870 и принимает команды в JSON, а в ответ шлёт состояние робота 50 раз в секунду.
Клиент может быть на любом языке, на хосте, в другом контейнере или на другом компьютере.

```bash
NET=host ./run.sh example udp_bridge g1        # терминал 1: окно G1 + сервер на порту 9870
python3 examples/udp_client.py --joint left_elbow --amp 0.6    # терминал 2, на хосте (нужен только python3)
```

Клиент качает локоть синусом и печатает:

```
робот g1, приводы: left_hip_pitch, left_hip_roll, left_hip_yaw, left_knee, …
t_sim=   2.96  left_elbow: цель    34.3°  факт    31.8°  момент   -0.24 Н·м  база z=0.913 м
t_sim=   3.47  left_elbow: цель    -3.2°  факт     8.5°  момент   -1.12 Н·м  база z=0.913 м
t_sim=   3.97  left_elbow: цель   -34.2°  факт   -32.4°  момент    0.24 Н·м  база z=0.913 м
t_sim=   4.48  left_elbow: цель     4.1°  факт    -6.2°  момент    0.63 Н·м  база z=0.913 м
```

`NET=host` нужен, чтобы порт контейнера был виден на хосте как `127.0.0.1:9870`. Без него можно пробросить порт:
`DOCKER_ARGS="-p 9870:9870/udp" ./run.sh example udp_bridge g1`. С другого компьютера: `--host <IP хоста>`
(откройте порт в файрволе: `sudo ufw allow 9870/udp`).

**Протокол** — одна команда JSON в одной датаграмме:

| Команда | Что делает |
|---|---|
| `{"info": true}` | ответ: `{"robot", "actuators": [имена], "ctrlrange": [[мин, макс], …], "rate"}` |
| `{"ctrl": {"left_elbow": 0.5, "right_elbow": -0.3}}` | цели приводов по именам (рад или м; лишнее обрезается по пределам) |
| `{"ctrl": [0.0, 0.1, …]}` | все цели сразу, в порядке `actuators` |
| `{"reset": true}` | вернуть исходную позу |
| `{"push": [0, 200, 0]}` | толкнуть корень робота силой (Н) на 0.1 с |

Состояние (рассылается всем, кто прислал хоть одну команду):
`{"t": время, "q": [углы приводов], "dq": [скорости], "tau": [моменты], "base_pos": [x, y, z], "base_quat": [w, x, y, z], "ncon": контактов}`.

Проверка без Python, из терминала: `echo '{"ctrl": {"left_elbow": 1.0}}' | nc -u -w1 127.0.0.1 9870`.

**ROS 2**: напишите на хосте ноду-переводчик — подписка на `sensor_msgs/JointState` с целями → `{"ctrl": {...}}`,
состояние из UDP → публикация `JointState`. Имена приводов совпадают с именами суставов без суффикса `_joint`.

## 16. Файлы: скриншоты, сохранение сцены

Рабочая папка контейнера — `/work`. Это папка `out/` рядом с `run.sh` (или `OUT_DIR`). Всё, что сохраняет
окно MuJoCo, попадает туда и принадлежит вашему пользователю. Папка `models/` видна в контейнере как `/models`
только для чтения.

| Действие | Файл на хосте |
|---|---|
| Ctrl+P или File → Screenshot | `out/screenshot.png` (перезаписывается при каждом снимке) |
| File → Save mjb | `out/mjmodel.mjb` (бинарная модель, ≈125 МБ для G1) |
| Ctrl+M / File → Print model | `out/MJMODEL.TXT` |
| Ctrl+D / File → Print data | `out/MJDATA.TXT` |
| `./run.sh test` | `out/selftest/*.png` |
| `./run.sh g1 --save-xml g1_scene.xml` | `out/g1_scene.xml` (так же для `h2`, `zbot`, `robot`) |
| ошибки MuJoCo (если окно не открылось) | `out/MUJOCO_LOG.TXT` |

**File → Save xml** для этих роботов не работает: MuJoCo пишет `No XML model loaded`, потому что сцена
собирается программно, а не читается из XML-файла. Используйте опцию `--save-xml`. В сохранённом файле пути
к мешам указывают внутрь контейнера (`/opt/gumanoid/...` или `/models/...`), поэтому открывать его нужно там же:
`./run.sh viewer g1_scene.xml`.

## 17. Частые проблемы

**`permission denied while trying to connect to the Docker daemon socket`**
Пользователь не в группе `docker`: `sudo usermod -aG docker $USER`, затем выйти из системы и войти снова.

**`run.sh: образ gumanoid-sim не найден`** — образ ещё не собран (`./build.sh`) или загружен под другим
именем (`docker images`, затем `IMAGE=имя ./run.sh`).

**Сборка: `failed to resolve source metadata for docker.io/...`, `lookup registry-1.docker.io ... server misbehaving`,
`TLS handshake timeout`** — демон Docker не может скачать базовый образ `ubuntu:24.04` с Docker Hub. Варианты:
- `build.sh` сам пробует скачать его через прокси терминала (`docker/pull-image.py`). Если интернет у вас через
  прокси, задайте его в терминале и повторите: `export HTTPS_PROXY=http://адрес:порт HTTP_PROXY=http://адрес:порт; ./build.sh`.
  Вручную: `python3 docker/pull-image.py ubuntu:24.04`;
- укажите прокси **демону** Docker (переменных окружения в терминале ему недостаточно):
  ```bash
  sudo mkdir -p /etc/systemd/system/docker.service.d
  printf '[Service]\nEnvironment="HTTP_PROXY=http://127.0.0.1:12334" "HTTPS_PROXY=http://127.0.0.1:12334" "NO_PROXY=localhost,127.0.0.1"\n' \
    | sudo tee /etc/systemd/system/docker.service.d/http-proxy.conf
  sudo systemctl daemon-reload && sudo systemctl restart docker
  ```
  (адрес и порт — вашего прокси);
- или пропишите зеркало Docker Hub в `/etc/docker/daemon.json`: `{"registry-mirrors": ["https://<зеркало>"]}`,
  затем `sudo systemctl restart docker`;
- или перенесите базовый образ файлом: на другом компьютере `docker save ubuntu:24.04 -o ubuntu2404.tar`,
  здесь `docker load -i ubuntu2404.tar`.

**Сборка падает на первом `apt-get update`: `At least one invalid signature was encountered`, `Couldn't create thread`,
`Operation not permitted`** — слишком старый Docker (ниже 20.10.10), обычно на необновлённой Ubuntu 20.04.
Обновите Docker ([пункт 2.4](#24-ubuntu-2204-и-2004)).

**Сборка падает на `pip install` или `git clone`** — нет доступа к PyPI или GitHub. Задайте прокси в терминале
(`export HTTPS_PROXY=http://адрес:порт HTTP_PROXY=http://адрес:порт`) и повторите `./build.sh`.

**`error: externally-managed-environment`** при `pip install` — так Ubuntu 24.04 защищает системный Python.
В этом образе пакеты ставятся в `/opt/venv`; если вы правили `Dockerfile`, ставьте через `pip` из venv (он
первый в `PATH`), а не `pip3 install --user`.

**`could not select device driver "" with capabilities: [[gpu]]`** — не установлен или не настроен
`nvidia-container-toolkit` ([раздел 3](#3-видеокарта-nvidia-по-желанию)). Временно: `GPU=dri ./run.sh` или `GPU=cpu ./run.sh`.

**`переменная DISPLAY пуста`**, `GLFWError: (65550) b'X11: Failed to open display :0'`,
`ERROR: could not initialize GLFW`, `Authorization required` — нет доступа к экрану:
- запускайте из терминала на рабочем столе, а не по ssh и не из `sudo`;
- выполните `xhost +SI:localuser:$USER` и повторите;
- в крайнем случае `xhost +local:` (разрешает окна всем локальным пользователям; вернуть — `xhost -local:`).

**`libGL error: MESA-LOADER: failed to open iris` / `radeonsi`**, `failed to load driver`, чёрное окно — не
работает аппаратная отрисовка Intel/AMD в контейнере. Проверьте `./run.sh glinfo`: строка `OpenGL renderer`
покажет видеокарту. Попробуйте `GPU=cpu ./run.sh` — медленнее, но работает везде.

**Ноутбук с NVIDIA и встроенной графикой.** `run.sh` сам включает PRIME offload (строка запуска
заканчивается на `(PRIME offload)`). Если окно чёрное или не открывается, попробуйте `PRIME=0 ./run.sh`,
`GPU=dri ./run.sh` или в настройках NVIDIA (`nvidia-settings` → PRIME Profiles) выберите режим On-Demand или
Performance.

**Wayland.** В Ubuntu 24.04 окно открывается через XWayland, `DISPLAY` там задан. Если что-то не работает, на
экране входа нажмите ⚙ (внизу справа) и выберите сеанс «Ubuntu on Xorg».

**Окно маленькое, робот обрезан** — разверните окно (двойной щелчок по заголовку), скройте левую панель (Tab),
уменьшите шрифт в Option → Font, приблизьте или отдалите камеру колесом, Ctrl+A вернёт камеру в исходный вид.

**Не вижу ползунков** — в правой панели щёлкните по заголовку **Control** или нажмите Alt+C. Если правой
панели нет совсем, нажмите Shift+Tab.

**Клавиши не работают** — щёлкните по 3D-сцене, чтобы окно стало активным. Если курсор стоит в текстовом
поле панели (например, Watch), нажмите Esc или щёлкните по сцене.

**G1/H2 падают в режиме `--free`** — так и должно быть, см. [раздел 9](#9-режимы-подвес-подвеска-свободно). Чтобы
стоять на полу, используйте `--band`.

**Своя модель не открывается** — [раздел 13.5](#135-если-модель-не-открывается).

**`udp_client.py`: нет ответа от 127.0.0.1:9870/udp** — сервер запущен без `NET=host` (порт не виден хосту) или
ещё не стартовал; запустите `NET=host ./run.sh example udp_bridge g1` и дождитесь строки `udp_bridge: … порт 9870/udp`.

**Очень медленно** — проверьте `./run.sh glinfo`: если там `llvmpipe`, рисует процессор. Выключите тени (S) и
отражения (R), уменьшите окно.

**Удалённый доступ по ssh** не поддерживается: `run.sh` рассчитан на локальный экран. Для удалённой работы
используйте удалённый рабочий стол (NoMachine, VNC, RDP) и запускайте `run.sh` внутри него. Без окна
(`--headless`, `test`, `udp_bridge --headless`) всё работает и по ssh: `docker run --rm gumanoid-sim test`.

## 18. Как это устроено, изменение и удаление

- `Dockerfile` собирает образ на `ubuntu:24.04`, Python-пакеты — в venv `/opt/venv`. Модели лежат в
  `/opt/gumanoid/zeroth-01-build` и `/opt/gumanoid/xr_teleoperate/assets`, скрипты — в `/opt/gumanoid` (он же
  в `PYTHONPATH`, поэтому свои скрипты могут делать `from robot_sliders import load_robot`). Точка входа —
  `/opt/gumanoid/docker/sim` (команда `sim`): `docker run gumanoid-sim g1` выполняет `sim g1`.
- Скрипты `*_sliders.py` берут исходную модель, добавляют пол, свет и по одному позиционному сервоприводу на
  сустав (ползунок = цель, пределы = пределы сустава, Kp/Kd и предельный момент — как у реальных моторов или
  подобранные). Самостолкновения звеньев выключены, с полом сталкиваются все звенья.
- Скрипты работают и без Docker: `python3 g1_sliders.py` при установленных `mujoco==3.15.0` и `numpy` (нужен
  Python 3.10 или новее, то есть не на Ubuntu 20.04 — там только через Docker). Путь к
  моделям Unitree задаётся переменной `XR_TELEOP_ASSETS` (по умолчанию `~/xr_teleoperate/assets`), к своим
  моделям — `GUMANOID_MODELS` (по умолчанию `/models`).
- **Изменить** коэффициенты или поведение: отредактируйте нужный `*.py` и выполните `./build.sh`. Пересоберётся
  только слой со скриптами, это занимает секунды.
- **Версии** зафиксированы в `Dockerfile` (`mujoco==3.15.0`, коммиты моделей в `ARG ZEROTH_COMMIT`/`ARG XR_COMMIT`).
  Поднимать версию MuJoCo без проверки (`./run.sh test`) не стоит: его API меняется от версии к версии.
- **Удалить:** `docker rmi gumanoid-sim`, затем удалить папку проекта, команду и ярлык, которые создал
  `install.sh`: `rm ~/.local/bin/gumanoid ~/.local/share/applications/gumanoid-sim.desktop`. Контейнеры
  удаляются сами (`--rm`). Освободить кэш сборки: `docker builder prune`. Docker и NVIDIA Container Toolkit
  остаются в системе; удалить их — `sudo apt remove docker-ce nvidia-container-toolkit` (или `docker.io`).
- `run.sh` выбирает графику сам: NVIDIA (если есть драйвер и NVIDIA Container Toolkit), иначе встроенная
  Intel/AMD, иначе процессор. Если контейнер с NVIDIA не запускается (сломан toolkit, драйвер обновился без
  перезагрузки), `run.sh` сразу повторяет запуск без неё. Только что добавленному в группу `docker`
  пользователю `run.sh` и `build.sh` дают группу через `sg docker`, без перезахода в систему.

Проверено (октябрь 2026) на ноутбуке с NVIDIA RTX 5060 Laptop и встроенной графикой Intel (Raptor Lake), хост — Ubuntu 24.04.4, Docker 29, образ — Ubuntu 24.04.5 (Mesa 25.2.8). Во всех трёх режимах (`GPU=nvidia` с PRIME, `GPU=dri`, `GPU=cpu`) самопроверка проходит 27/27; окна G1, H2, Zeroth-01, `robot` (H1, Go2 из Menagerie), меню моделей, оба примера (`script_control`, `udp_bridge` с клиентом на хосте) открываются и работают. `install.sh` проверен на нём же, с уже установленными Docker и NVIDIA Container Toolkit, и в режиме без NVIDIA (запасной запуск на встроенной графике, `GPU=cpu`).
